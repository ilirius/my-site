## Context

Проект находится в процессе миграции:
- **Текущее состояние**: старый код в `src/` (CRA, React, i18next, SCSS) содержит работающую главную страницу и заготовки остальных
- **Целевое состояние**: Next.js 16 SSG в `apps/web/` с архитектурой FSD и Atomic Design в @repo/ui
- **Монорепо**: уже настроено — Turborepo + pnpm, два Next.js-приложения (web, docs) и три пакета (ui, eslint-config, typescript-config)
- См. proposal.md — Why для мотивации

## Goals / Non-Goals

**Goals:**
- Задокументировать целевой техстек, архитектуру и план миграции в виде спецификаций
- Создать единый источник правды для разработки

**Non-Goals:**
- Не пишем код — только спецификации
- Не изменяем структуру монорепо
- Не затрагиваем apps/docs

## Decisions

### Decision 1: FSD вместо Feature-based или Layer-based

**Выбрано**: Feature-Sliced Design (FSD)
**Альтернативы**:
- Простая группировка по типам (components/, pages/, hooks/) — не масштабируется
- Feature-based (features/home/, features/about/) — нет чёткой стратификации

**Обоснование**: FSD уже знаком автору, обеспечивает изоляцию слоёв и предсказуемую структуру. Подходит для проекта из 6 страниц.

### Decision 2: Atomic Design в @repo/ui, а не в apps/web

**Выбрано**: Atomic Design вынесен в отдельный пакет @repo/ui
**Альтернативы**:
- Хранить компоненты внутри apps/web — переиспользование между web и docs невозможно
- Использовать другой подход (например, классическая папка components/) — Atomic Design даёт чёткую градацию сложности компонентов

**Обоснование**: @repo/ui — общий пакет для обоих Next.js-приложений. Atomic Design задаёт понятную иерархию: atoms → molecules → organisms.

### Decision 3: Next.js App Router (не Pages Router)

**Выбрано**: App Router (Next.js 16)
**Альтернативы**: Pages Router — устаревший, не рекомендуется для новых проектов
**Обоснование**: App Router — современный стандарт Next.js, файловая маршрутизация, React Server Components (даже при SSG)

### Decision 4: SCSS + CSS Modules, не CSS-in-JS

**Выбрано**: SCSS + CSS Modules
**Альтернативы**: Tailwind, styled-components, vanilla-extract
**Обоснование**: Уже используется в проекте (src/styles/), проще мигрировать, знаком автору. CSS Modules дают изоляцию без дополнительных зависимостей.

### Decision 5: SSG, не SSR

**Выбрано**: Статическая генерация (SSG)
**Альтернативы**: SSR, ISR
**Обоснование**: Сайт-портфолио — полностью статический контент без серверной логики. SSG = максимальная производительность и zero-cost хостинг (Vercel, GitHub Pages и т.д.)

## Risks / Trade-offs

- **[Миграция]** Перенос кода может занять время, в течение которого `src/` и `apps/web/` сосуществуют → директория `src/` чётко промаркирована как наследие, задачи миграции зафиксированы в migration-plan
- **[Консистентность]** FSD + Atomic Design — две методологии, которые нужно согласовать → FSD-слои содержат композицию, @repo/ui — атомарные компоненты; граница: widget использует organisms из @repo/ui
- **[Документация]** Спецификация может расходиться с реальностью при долгой разработке → регулярная синхронизация через openspec sync
